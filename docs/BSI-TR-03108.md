# BSI TR-03108 mapping

How Sovereign relates to BSI TR-03108 "Secure Email Transport", **version 2.0
of 1 June 2023**, and its test specification TR-03108-P 2.0. Until every
requirement below is met and tested, the documentation says "TLS
configuration based on BSI TR-03108", not "compliant".

The TR is written for commercial email service providers. A private server
is an "operator of an MHS" in its glossary, so the organisational
requirements (13 to 16) apply only in spirit. The technical ones (01 to 12)
are what this project can implement.

Every TLS parameter must also meet **BSI TR-03116-4**, which BSI updates
every year; the TR says the latest version counts. It has not yet been
compared line by line with our settings (see "Next steps").

## Requirements

Status: **met** (implemented and tested), **partly**, **gap**, or
**operator** (depends on DNS or organisation, documented only).

| ID | Level | Requirement (short) | Status | Where / what is missing |
|---|---|---|---|---|
| 01-M | MUST | Client access only over TLS (RFC 8314), TLS per TR-03116-4. Implicit TLS must be offered: SUBMISSIONS (465), IMAPS (993). Encourage it through SRV records, autoconfig or autodiscover, and documentation; those services run on premises. Webmail over HTTPS. Delivery failures reported by mail with RFC 3463 codes. | met | IMAPS 993, SUBMISSIONS 465 and HTTPS webmail. Thunderbird's autoconfig lists 465 before 587; autodiscover and the Apple profile point to 465 only. No RFC 6186 SRV records in the README (the TR says "and / or", autoconfig and autodiscover suffice). Bounces with RFC 3463 codes: Postfix default. No POP3, so its rules don't apply. |
| 02-R | SHOULD | Also offer STARTTLS (SUBMISSION 587, IMAP 143) for older clients, TLS per TR-03116-4. | met | `roles/postfix` (587), `roles/dovecot` (143, `ssl = required`, so no login before STARTTLS). |
| 03-M | MUST | Inbound STARTTLS from other servers, TLS per TR-03116-4, PFS preferred. | met | `smtpd_tls_security_level = may`, ECDHE suites only (`postfix_tls12_ciphers`). Plaintext stays possible for senders without TLS, which 4.3.2 allows. |
| 04-M | MUST | DNSSEC-validating resolver; outbound opportunistic TLS with STARTTLS; prefer PFS. | met | `roles/unbound` (validating, `trust-ad`), `smtp_tls_security_level = dane`. |
| 05-M | MUST | DNSSEC-signed zones of the mail domain and of the MX host's domain; TLSA records for the MX. Recommended: a `3 x x` and a `2 x x` record, short TTL (e.g. 600 s). | operator | README asks for `_25._tcp` TLSA `3 1 1` in a signed zone, the key stays across renewals. Not mentioned: a second `2 1 1` record for the issuing CA, and the short TTL. Signing the zones is the DNS provider's job. |
| 06-M | MUST | Outbound DANE (RFC 7672): with valid TLSA records, no delivery without TLS or without a verified certificate. | met | `smtp_dns_support_level = dnssec`, `smtp_tls_security_level = dane`; tested in `test_dane.py` (correct TLSA record verified, wrong one defers the mail, mixed and unusable MX sets) and `test_unbound.py` (bogus zones fail). |
| 07-R | SHOULD | Publish an MTA-STS policy. | met | `roles/mta_sts`, `test_web.py`, `test_multidomain.py`. |
| 08-R | SHOULD | Use MTA-STS outbound; **contrary to RFC 8461, do not accept wildcard certificates when fetching the policy**. | partly | `postfix-mta-sts-resolver` behind `sovereign-tls-policy`. It fetches policies with the normal certificate check, which most likely accepts wildcard certificates; not checked in its code yet. |
| 09-M | MUST | **Send TLS-RPT reports** (RFC 8460) to domains that ask for them; partial reports are fine. HTTPS delivery per RFC 2818 and TR-03116-4. | **gap** | Postfix 3.10 in Debian 13 has the client side (`smtp_tlsrpt_enable`, `libtlsrpt0` is packaged), but the reporting daemon that collects the data and sends the reports (`tlsrpt-reporter`) is not in Debian. `postfix-mta-sts-resolver` 1.5.0 in Debian 13 can deliver MTA-STS results (`tlsrpt: true`); DANE results come from Postfix. A Debian packaging draft exists (builds and works on unstable); it needs an ITP and an uploader. Sovereign enables TLS-RPT only once the package is in Debian. |
| 10-M | MUST | Publish a TLS-RPT policy, reports by mail only (`mailto:`), never HTTPS. The receiving mailbox SHOULD NOT enforce TLS through DANE or MTA-STS. | partly | README: `_smtp._tls` TXT with `rua=mailto:postmaster@<domain>`. That mailbox is on a domain with DANE and an MTA-STS policy in `enforce` mode, which the SHOULD NOT advises against: the report about a broken TLS setup may not get through for the same reason. |
| 11-R | SHOULD | Evaluate the reports. | gap | Nothing parses incoming TLS-RPT reports. |
| 12-R | SHOULD | Certificates from a CA that meets TR-03116-4. | operator | Let's Encrypt by default; whether it qualifies is not assessed here. |
| 13-M | MUST | Security concept (TKG § 165 or equivalent), ISMS recommended. | operator | Not in scope of the software. |
| 14-M | MUST | Operation under GDPR / TTDSG, within the EU. | operator | Log retention is still open (see the log rotation work in `STATUS.md`). |
| 15-M | MUST | Notify customers of security incidents (TKG § 169). | operator | |
| 16-M | MUST | Tell customers which other providers meet the TR. | operator | |

Exceptions in the TR itself: TLS sessions may live longer than TR-03116-4's 48
hours (IMAP IDLE needs it), and weaker TLS versions and suites may be offered
for opportunistic SMTP if they get the lowest priority. Sovereign offers only
TLS 1.2 and 1.3 on every channel, so it doesn't use the second exception.

## What a certification would ask for (TR-03108-P)

The test lab works from an "Implementation Conformance Statement": for each
channel separately (browser, submission, IMAP, inbound SMTP, outbound SMTP
without and with DANE) the TLS versions, cipher suites, minimum key lengths,
elliptic curves and signature algorithms, plus the DNSSEC algorithms, the
supported TLSA parameter combinations, the TLS-RPT organisation name and the
physical locations. Anything the lab finds beyond the declaration is noted in
the report. Test modules: A user interface, B DNSSEC, C DANE outbound,
D DANE inbound, E TLS inbound, F TLS outbound, G TLS-RPT inbound,
H TLS-RPT outbound, I MTA-STS inbound, J MTA-STS outbound, and the security
concept.

Our settings, from the role defaults (identical for Postfix, Dovecot and
nginx):

- TLS 1.2: `ECDHE-ECDSA-AES256-GCM-SHA384`, `ECDHE-ECDSA-AES128-GCM-SHA256`,
  `ECDHE-RSA-AES256-GCM-SHA384`, `ECDHE-RSA-AES128-GCM-SHA256`
- TLS 1.3: `TLS_AES_256_GCM_SHA384`, `TLS_AES_128_GCM_SHA256`
- Groups: `secp256r1`, `secp384r1`
- Certificate: ECDSA P-256
- Signature algorithms: **not restricted**, so OpenSSL's defaults apply. They
  likely include Ed25519 and Ed448, which TR-03116-4 does not list. To check
  with a scan.

## Next steps

1. ~~SUBMISSIONS on 465~~ (01-M): done.
2. **Compare with the current TR-03116-4** and pin the signature
   algorithms (`ssl_conf_command SignatureAlgorithms` in nginx,
   `tls_config_file` in Postfix, `ssl_options`/OpenSSL config in Dovecot).
3. **A TLS scan as a test**: `testssl.sh` against every channel in the
   Molecule VM, checked against an allow list. Its output is also the
   Implementation Conformance Statement a lab asks for.
4. **TLS-RPT sending** (09-M): get `tlsrpt-reporter` into Debian (packaging
   draft done, ITP and upload open), then `trixie-backports`; then enable it
   in the postfix and mta_sts roles, with a test that a report arrives.
5. **TLS-RPT receiving** (10-M, 11-R): document a report address on a
   domain without enforced TLS, and decide whether reports get evaluated.
6. **DNS documentation** (05-M): a second TLSA record `2 1 1` for the
   issuing CA's key and a short TTL. With Let's Encrypt, the intermediate
   changes between issuers, so this needs care.
7. **MTA-STS policy fetch without wildcard certificates** (08-R): check
   what `postfix-mta-sts-resolver` allows to configure.
